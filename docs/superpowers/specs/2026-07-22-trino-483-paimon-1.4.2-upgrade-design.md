# Trino 483 and Paimon 1.4.2 Upgrade Design

**Date:** 2026-07-22
**Status:** Approved

## Context

The local `paimon-trino` fork currently packages Paimon 1.4.1 and was adapted
for Trino 481, although the default `trino.version` remains 476. A clean
diagnostic compile against Trino 483 and Paimon 1.4.2 proves that dependency
resolution succeeds, but compilation fails on SPI changes introduced by Trino
482 and 483.

The incompatible areas are split scheduling and dynamic filters, page source
and page sink providers, table-function processors, removed `Type` methods,
and the bit-packed block null representation. Trino 483 also aligns with JDK
25, Airlift 439, and Slice 2.8.

## Goals

- Make Trino 483 and Paimon 1.4.2 the connector's explicit default versions.
- Compile, test, and package the connector on JDK 25.
- Preserve the fork's existing Paimon behavior and Hive compatibility JAR
  packaging.
- Build and publish a versioned runtime image only after source validation.
- Update the repo-managed `trino-paimon` deployment to the validated image.
- Prove the deployed connector with metadata, read, and write SQL.

## Non-Goals

- Refactor unrelated connector behavior.
- Change the Paimon warehouse, catalog name, authentication model, public VIP,
  TLS contract, or Trino worker sizing.
- Commit developer-specific Maven mirror configuration.
- Remove the currently deployed image before the replacement is verified.

## Selected Approach

Adapt the current fork directly and pin the complete compatible dependency set:

- Trino 483
- Paimon parent and bundle 1.4.2
- JDK 25
- Airlift 439
- Slice 2.8

This is preferred over waiting for upstream because the Apache repository still
targets Trino 476 and Paimon 1.3.1. It is preferred over a compile-only patch
because the changed SPIs participate in runtime reads, writes, split scheduling,
and block construction.

## Source Compatibility Changes

### Split scheduling

Update `TrinoSplitManager` to accept dynamic-filter columns and update
`TrinoSplitSource` to receive a `DynamicFilterSnapshot` on each batch request.
Preserve the existing Paimon split planning semantics; the snapshot is used
only where the connector can safely translate it to Paimon predicates.

### Page sources and sinks

Implement only the non-deprecated Trino 483 provider signatures. Pass through
the new page-source memory context and optional table credentials without
changing Paimon read or write semantics. Remove overrides for signatures that
Trino 482 deleted.

### Type and block APIs

Replace removed `Type.getTypeSignature()` calls with the Trino 483 equivalent.
Construct blocks through supported builders where practical. Where the existing
code must copy null vectors, convert boolean null arrays to Trino 483's
bit-packed validity representation without changing row positions or values.

### Table functions

Update the table-changes processor provider to the remaining Trino 483 method
contract while preserving the current table-changes behavior.

### Dependency enforcement

Keep dependency enforcement enabled in the committed build. If Paimon 1.4.2's
parent enforcer rejects safe Trino 483 dependencies, add the narrowest explicit
dependency-management or exclusion adjustment that produces a clean dependency
tree. Do not globally disable Maven Enforcer in the project.

## Validation

Source validation proceeds in increasing scope:

1. Compile main sources against the pinned defaults.
2. Run focused tests for split, page source, block conversion, and write paths.
3. Run the complete Maven test suite.
4. Package the plugin distribution and inspect its dependency contents.
5. Build a Trino 483 runtime image containing the packaged connector.

Maven may use `/tmp/paimon-trino-aliyun-settings.xml`, configured for Aliyun
first and Maven Central fallback. This file remains outside Git.

## Deployment

After all source validation passes:

1. Add a new immutable image tag containing Trino 483, Paimon 1.4.2, and the
   connector commit identifier.
2. Build and push the image through the existing RKE2/BuildKit workflow.
3. Update `storage-ops/trino-paimon` values, documentation, and smoke assertions
   to the exact image tag.
4. Render the Helm chart and run repository smoke tests.
5. Upgrade the `trino-paimon` release and wait for coordinator and workers to
   become ready.

The prior image tag remains available as the rollback target. If rollout or SQL
validation fails, restore that tag and redeploy rather than debugging against a
partially available production endpoint.

## SQL Acceptance Checks

Run authenticated SQL against the deployed HTTPS endpoint:

1. `SELECT version()` reports Trino 483.
2. `SHOW CATALOGS` includes `paimon`.
3. `SHOW SCHEMAS FROM paimon` succeeds.
4. `SHOW TABLES FROM paimon.<existing_schema>` succeeds.
5. A `SELECT count(*)` from an existing Paimon table succeeds.
6. Create a uniquely named validation table, insert deterministic rows, read
   them back, and verify count and aggregate values.
7. Drop only the validation table created by this rollout.

No existing table is mutated by the acceptance checks.

## Success Criteria

- The source branch builds and tests with committed Trino 483 and Paimon 1.4.2
  defaults and with Maven Enforcer enabled.
- The packaged connector starts inside the Trino 483 runtime image.
- All coordinator and worker pods are ready after the Helm upgrade.
- Every SQL acceptance check passes through the deployed service.
- The old image remains usable for rollback until validation completes.
